# 需求文档：IPTV M3U 聚合器 Go 重构

## 简介

本文档规定了将现有的基于 Python 的 IPTV M3U 聚合平台重构为 Go 的需求。重构保持所有现有功能，同时改进性能、并发处理和部署特性。该系统聚合多个 IPTV M3U 订阅源，对频道进行去重，测试流可用性，并提供 Web UI 和 API 接口用于管理和消费。

## 术语表

- **M3U 格式**：多媒体文件的播放列表格式，通常用于带有 EXTINF 元数据的 IPTV 流
- **订阅源**：指向包含 IPTV 频道定义的 M3U 文件的 URL
- **频道**：单个 IPTV 流条目，包含元数据（名称、分组、logo、URL）
- **聚合**：将来自多个源的频道合并并去重的过程
- **流测试**：验证频道 URL 可用性和响应性的过程
- **深度检查**：检测 HLS 流循环和卡顿的高级流测试
- **工作 URL**：已验证为可访问和响应的频道 URL
- **调度器**：在配置的时间间隔执行周期性任务（更新、测试）的组件
- **Web UI**：用于管理订阅和查看频道的 HTML/CSS/JavaScript 界面
- **API**：用于以编程方式访问聚合频道和管理功能的 RESTful 端点
- **导出**：从聚合频道生成 M3U 或 JSON 文件的过程
- **持久化**：将订阅、频道和配置数据存储到磁盘

## 需求

### 需求 1：订阅源管理

**用户故事**：作为平台管理员，我想管理 IPTV 订阅源，以便我可以控制哪些源被聚合并维护频道数据库。

#### 验收标准

1. 当管理员添加新的订阅源 URL 时，系统应存储它及其元数据（名称、启用状态）并持久化到磁盘
2. 当管理员检索订阅列表时，系统应返回所有存储的订阅及其当前状态（活跃、失败、未测试）
3. 当管理员更新订阅源 URL 或元数据时，系统应修改存储的订阅并持久化更改
4. 当管理员删除订阅源时，系统应从存储中删除它并防止从该源进行进一步聚合
5. 当添加或修改订阅源时，系统应在接受前验证 URL 格式
6. 当系统启动时，系统应从磁盘加载所有持久化的订阅到内存

### 需求 2：M3U 文件解析和频道提取

**用户故事**：作为系统组件，我想从远程源解析 M3U 文件，以便我可以提取频道元数据用于聚合。

#### 验收标准

1. 当系统从订阅源 URL 获取 M3U 文件时，解析器应使用可配置的超时时间（默认 30 秒）检索内容
2. 当解析器接收 M3U 内容时，解析器应提取所有 EXTINF 元数据行和频道 URL
3. 当解析 EXTINF 行时，解析器应提取 tvg-id、tvg-name、tvg-logo、group-title 和频道名称属性
4. 当提取频道 URL 时，解析器应将其与其源订阅源 URL 关联以进行跟踪
5. 当解析器遇到格式错误的 M3U 内容时，解析器应跳过无效条目并继续处理有效条目
6. 当解析完成时，解析器应返回包含所有提取元数据的频道对象列表

### 需求 3：频道聚合和去重

**用户故事**：作为系统组件，我想从多个源聚合频道并去重，以便用户看到统一的频道列表而不会有冗余。

#### 验收标准

1. 当聚合器从多个源接收频道时，聚合器应将它们合并为单个列表
2. 当检测到重复频道（基于名称或 tvg-id，取决于配置）时，聚合器应合并它们并保留所有可用的 URL
3. 当合并重复频道时，聚合器应使用可配置的阈值（默认 0.85）计算名称相似度
4. 当聚合完成时，聚合器应将统一的频道列表持久化到磁盘
5. 当系统启动时，聚合器应从磁盘加载持久化的频道列表
6. 当聚合频道时，聚合器应跟踪每个 URL 来自哪个源以便调试

### 需求 4：流可用性测试

**用户故事**：作为系统组件，我想测试频道流 URL 的可用性，以便用户可以识别工作频道，系统可以维护质量指标。

#### 验收标准

1. 当流测试器接收一批频道时，流测试器应并发测试每个 URL（最多达到 max_workers 限制，默认 10）
2. 当测试流 URL 时，流测试器应使用可配置的超时时间（默认 5 秒）尝试连接
3. 当流 URL 成功响应时，流测试器应将其标记为"在线"并记录响应时间
4. 当流 URL 无法响应或超时时，流测试器应将其标记为"离线"
5. 当启用深度检查时，流测试器应执行高级 HLS 流验证以检测循环和卡顿
6. 当深度检查检测到 HLS 流循环时，流测试器应将流标记为"离线"，尽管初始连接成功
7. 当频道有多个 URL 时，流测试器应测试所有 URL 并识别工作的 URL
8. 当测试完成时，流测试器应将测试结果持久化到频道数据
9. 当系统配置为 test_all_sources=true 时，流测试器应测试每个频道的所有 URL；否则仅测试主 URL

### 需求 5：周期性任务调度

**用户故事**：作为系统组件，我想安排周期性任务用于订阅更新和流测试，以便频道数据库保持最新，质量指标得到维护。

#### 验收标准

1. 当系统启动时，调度器应初始化配置的周期性任务而不立即执行它们
2. 当安排周期性任务时，调度器应在配置的时间间隔（小时、分钟或秒）执行它
3. 当更新任务执行时，调度器应获取所有启用的订阅、解析 M3U 文件并聚合频道
4. 当测试任务执行时，调度器应测试所有频道并持久化结果
5. 当手动触发任务时，调度器应立即执行它，无论计划如何
6. 当系统关闭时，调度器应优雅地停止所有运行的任务

### 需求 6：频道数据导出

**用户故事**：作为用户，我想以标准格式导出聚合频道，以便我可以将它们与 IPTV 播放器和其他应用程序一起使用。

#### 验收标准

1. 当用户请求 M3U 导出时，导出器应生成包含所有频道元数据的有效 M3U 文件
2. 当用户请求 JSON 导出时，导出器应生成包含完整频道数据的 JSON 文件
3. 当导出请求中 only_working=true 时，导出器应仅包含标记为"在线"的频道
4. 当导出完成时，导出器应使用时间戳文件名将文件保存到磁盘
5. 当用户请求导出列表时，导出器应返回所有先前生成的导出文件及其元数据
6. 当用户删除导出文件时，导出器应从磁盘删除它

### 需求 7：Web 用户界面

**用户故事**：作为用户，我想通过 Web 界面与系统交互，以便我可以管理订阅和查看频道信息而无需命令行访问。

#### 验收标准

1. 当用户访问 Web 界面时，系统应显示包含聚合统计信息的仪表板（总订阅数、频道数、分组数、在线/离线计数）
2. 当用户导航到订阅页面时，系统应显示所有订阅及其状态和频道计数
3. 当用户导航到频道页面时，系统应显示所有频道，可按分组、状态（在线/离线/未测试）过滤，并按名称搜索
4. 当用户点击测试单个频道时，系统应执行测试并使用结果更新 UI
5. 当用户点击测试所有频道时，系统应启动批量测试并提供进度反馈
6. 当用户点击更新订阅时，系统应启动更新过程并提供状态反馈
7. 当用户导航到导出页面时，系统应显示可用的导出文件并允许创建新导出
8. 当用户导航到设置时，系统应显示所有可配置参数并允许修改

### 需求 8：RESTful API 端点

**用户故事**：作为开发者，我想以编程方式访问聚合频道，以便我可以将系统与 IPTV 播放器和其他应用程序集成。

#### 验收标准

1. 当客户端请求 GET /api/playlist.m3u 时，API 应返回包含仅在线频道的有效 M3U 文件
2. 当客户端请求 GET /api/channels 时，API 应返回所有频道的 JSON 数组，可选按分组或状态过滤
3. 当客户端请求 GET /api/subscriptions 时，API 应返回所有订阅的 JSON 数组及其状态
4. 当客户端请求 GET /api/stats 时，API 应返回聚合统计信息（总频道数、在线计数、离线计数等）
5. 当客户端请求 POST /api/subscriptions 时，API 应创建新订阅并返回创建的对象
6. 当客户端请求 DELETE /api/subscriptions/{id} 时，API 应删除订阅并返回成功状态

### 需求 9：配置管理

**用户故事**：作为系统管理员，我想配置系统参数，以便我可以为不同的部署场景自定义行为。

#### 验收标准

1. 当系统启动时，系统应从 config.json 文件加载配置（如果存在）
2. 当配置缺失时，系统应使用合理的默认值并创建配置文件
3. 当用户通过 Web UI 修改设置时，系统应将更改持久化到 config.json
4. 当配置更新时，系统应将更改应用到运行的组件（调度器间隔、测试超时等）
5. 系统应支持配置：更新间隔、测试间隔、流测试超时、最大并发工作者、深度检查设置、聚合匹配策略和相似度阈值

### 需求 10：数据持久化

**用户故事**：作为系统组件，我想将所有数据持久化到磁盘，以便系统可以在重启后恢复状态并维护历史数据。

#### 验收标准

1. 当添加、修改或删除订阅时，系统应将更改持久化到 subscriptions.json
2. 当聚合或测试频道时，系统应将频道列表持久化到 channels.json
3. 当修改配置时，系统应将更改持久化到 config.json
4. 当系统启动时，系统应从磁盘加载所有持久化数据
5. 当数据文件损坏或缺失时，系统应使用空数据初始化并记录问题
6. 系统应在并发操作中维护数据一致性

### 需求 11：性能和并发

**用户故事**：作为系统操作员，我想系统高效处理并发操作，以便多个用户可以同时与系统交互而不会性能下降。

#### 验收标准

1. 当执行多个流测试时，系统应并发处理它们，最多达到配置的 max_workers 限制
2. 当 Web UI 在后台任务运行时请求数据时，系统应在不阻塞的情况下提供请求
3. 当多个用户同时访问 Web 界面时，系统应并发处理请求
4. 当从多个源聚合频道时，系统应并发获取和解析源
5. 系统应在 5 分钟内完成 1000 个频道的测试，使用默认配置（10 个并发工作者，5 秒超时）

### 需求 12：错误处理和日志

**用户故事**：作为系统操作员，我想要全面的错误处理和日志，以便我可以诊断问题并维护系统可靠性。

#### 验收标准

1. 当订阅获取失败时，系统应记录错误、将订阅标记为失败并继续处理其他订阅
2. 当流测试失败时，系统应记录错误并将流标记为离线
3. 当配置加载失败时，系统应记录错误并使用默认配置
4. 当数据持久化失败时，系统应记录错误并尝试重试
5. 系统应维护包含时间戳、级别、组件和消息的结构化日志
6. 当发生未处理的错误时，系统应记录它并继续操作而不崩溃

### 需求 13：与 Python 版本的向后兼容性

**用户故事**：作为系统操作员，我想 Go 版本与现有数据格式兼容，以便我可以从 Python 迁移到 Go 而不会丢失数据。

#### 验收标准

1. 当 Go 系统启动时，系统应读取由 Python 版本创建的 subscriptions.json
2. 当 Go 系统启动时，系统应读取由 Python 版本创建的 channels.json
3. 当 Go 系统启动时，系统应读取由 Python 版本创建的 config.json
4. 当 Go 系统导出数据时，系统应生成与 Python 版本相同格式的文件
5. 当用户从 Python 迁移到 Go 时，系统应保留所有订阅和频道数据
